# 01: Unified POS Order Settlement, Pessimistic Concurrency Locking & Settlement-Time Retained Deposit Accounting

**What to build:** Receptionists, stylists, and customers can book appointments, modify active POS orders, cancel reservations, and settle bills concurrently without risk of double-charging inventory, paying duplicate commissions, double-spending retained deposit credits, losing retained deposit credits on modified/unsettled draft orders, or crashing with duplicate order codes. All three POS order settlement entry points (standard counter checkout, walk-in `Quick Service Ticket`, and scheduled booking quick completion) execute through a single unified transactional settlement pipeline that acquires a pessimistic database write lock on the `Order` record before checking or transitioning its status to `PAID`. Whenever a customer's `Retained Deposit` (`creditBalance`) or `Cumulative Spend` (`totalSpent`) is read and mutated—during online `Booking` creation, `Booking` cancellation, or final `Order` settlement—the customer record is locked with a pessimistic write lock so concurrent requests serialize cleanly. During `Booking` check-in or `Walk-in Order` creation on the `Dispatch Board`, the customer's `Retained Deposit` is no longer deducted upfront on the draft `Order`; `depositDeducted` during active service reflects only the originating `Booking`'s paid 20% `Deposit`, and any available `Retained Deposit` is applied and deducted atomically only at final `Order` settlement (`PAID`) after all service items, retail items, and discounts are final. Cancelling a `Booking` from either the Customer Portal or the Admin/POS workspace uses one shared cancellation flow that releases Redis `Slot Locks` only when the booking was `PENDING_PAYMENT` and credits paid deposits to `Retained Deposit` under a customer row lock. Newly created POS `Orders` generate collision-resistant codes using a date prefix and random alphanumeric suffix (`ORD-yyyyMMdd-XXXXXX`).

**Blocked by:** None (can start immediately)

**Status:** complete

- [x] Standard POS counter checkout, walk-in `Quick Service Ticket` creation, and scheduled booking quick completion all delegate settlement through a single shared transactional settlement pipeline, removing the three duplicated settlement blocks.
- [x] Loading an `Order` for settlement acquires a pessimistic database write lock (`PESSIMISTIC_WRITE`); if the locked `Order` is already `PAID` or `CANCELLED`, the second concurrent request is rejected immediately without deducting `Branch Inventory` (`Opened Volume` or `Sealed Units`), creating duplicate `Commission Ledger` entries, or recording a second `Payment Transaction`.
- [x] Loading a customer record to apply/deduct `Retained Deposit` (`creditBalance`), credit a cancelled `Booking` `Deposit` into `creditBalance`, or increment `Cumulative Spend` (`totalSpent`) acquires a pessimistic database write lock (`PESSIMISTIC_WRITE`) so concurrent booking or settlement requests cannot double-spend the same credit balance.
- [x] Checking in a `Booking` or creating a `Walk-in Order` does not deduct from the customer's `Retained Deposit` (`creditBalance`) while the `Order` is in draft (`UNPAID`) state; adding or removing items or changing discounts on an active `Order` never reduces or destroys the customer's `creditBalance`, and available `creditBalance` is deducted once at final settlement (`PAID`).
- [x] Customer self-service `Booking` cancellation and staff-initiated `Booking` cancellation share a single domain cancellation flow that unlocks Redis `Slot Locks` only when the booking's prior status was `PENDING_PAYMENT` and credits any paid `Deposit` to `Retained Deposit` (`CREDITED`) under a pessimistic customer row lock, while removing redundant security-context customer resolution during booking creation.
- [x] POS `Order` code generation uses a date and random suffix format (`ORD-yyyyMMdd-XXXXXX`) verified for uniqueness rather than millisecond modulo arithmetic, preventing unique constraint failures across concurrent check-ins or multi-day operations.
- [x] Automated multi-threaded concurrency tests (`CountDownLatch`) verify that simultaneous checkout requests on the same `Order` and simultaneous `Booking` requests using the same customer's `Retained Deposit` succeed at most once and preserve exact inventory, commission, and credit balances.
